# 会议迭代交付与使用说明

本轮围绕运营项目关键任务、学校开拓、周期汇报及经营数据可核对性升级。沿用现有 Vue/FastAPI/PostgreSQL 和项目授权，数据库迁移 `61e8a4cf290d` 只新增表，原任务、节点、反馈、合同和学校记录保留。

## 功能入口与会议需求对应

| 编号 | 交付内容 | 入口 / 验证方式 |
|---|---|---|
| JC-01 | 试点工作流程与责任表 | 本文下一节；实际人员继续使用现有项目团队名单 |
| JC-02 | 沿用个人菜单/操作权限、项目成员与任务可见范围 | 系统管理、项目团队；测试使用不同账号验证列表/详情/反馈/报告 |
| JC-03 | 默认关键任务卡与简短反馈 | 运营项目 → 任务情况；进行中/已完成分组保留 |
| JC-04 | 节点独立进展、节点展开查看 | 任务详情 → 阶段节点；反馈时可选择具体节点，旧反馈仍为任务级 |
| JC-05 | 每天、每 2 天、每 3 天、每周、按节点反馈 | 布置任务/调整安排；每天 16:00 生成站内提醒，未完成及待回复保留为业务待办 |

| JC-08 | 默认本年，历史年份可选；卡片、下钻、导出共用条件 | 合同台账 → 签订年份；历史年只展示年度卡片，明确期间，历史合同保留 |
| JC-09 | 保存的源表与当前台账逐行对账 | 合同台账 → 来源对账；显示字段/回款差异、未对应及重复来源，按业务 ID 去重 |

| JC-15 | 复用企微派单队列、错误重试和当前权限检查 | 派发/转交任务触发；完成/暂停/作废/撤权后不再投递旧派单；外部触达须以实际租户回执为准 |
| JC-16 | 已完成历史、作废/恢复 | 继续使用现有记录；没有准确对象清单，不批量删除真实记录 |
| JC-17 | 同数据的任务卡和进度表、跨团队复用 | 任务情况 → 任务卡/进度表；其他团队新建运营项目并配置成员即可使用 |

小聚业务目录自动收录新查询和办理接口；写操作沿用具体执行单确认及服务端权限。WorkBuddy 的任务反馈增加可选节点编号与版本校验，创建任务支持新增反馈周期。

## 试点执行流程

| 环节 | 责任人 | 输入 | 输出 |
|---|---|---|---|
| 确认团队 | 现有授权管理员 / 项目负责人 | 现有实名成员、角色、任务可见范围 | 每人使用自己的账号，执行/管理/只读边界清晰 |
| 派单 | 项目管理者 | 简短事项、负责人、期限、完成要求、反馈周期、可选节点 | 原任务及通知；其他人不能因被提及自动获得权限 |
| 推进 | 任务负责人 | 做到哪一步、节点结果、下一步 | 任务/节点反馈留痕；后台按反馈更新下一轮期限 |
| 补要求 | 项目管理者 | 具体要求、指定执行成员 | 被指定人待回复；读取通知不会关闭要求 |
| 回复 | 被指定人本人 | 回复内容 | 该要求结束待回复；不替代任务进展与完成 |
| 完成 | 任务负责人或有权管理者 | 完成说明、全部节点确认 | 移出当前待办，保留完成时间和全部历史 |
| 学校开拓 | 项目执行成员 | 实际跟进日期、进展、问题及下一步 | 学校历史记录；补录与发生时间区分 |
| 学校落地 | 项目管理者 | 确认依据、已签约或运营中 | 转为存量，学校 ID、任务和跟进历史不变 |
| 汇报 | 系统定时或有权用户手动 | 已登记事实 | 个人/项目报告版本；每项可回查业务记录 |
| 经营核数 | 合同/财务资料负责人 | 已确认源表版本、台账口径 | 逐行差异；先核对再另行更正真实数据 |

用户本轮未提供新增成员名单或测试对象清单，部署保留现有成员与权限，没有执行会议里的模糊删除安排。

## 采用的规则

- 周期按北京时间自然日计算。每 2/3/7 天自创建或最近一次有效进展反馈起算；每天反馈保留原有当天待反馈逻辑。每周是滚动 7 天，不是固定某个星期。按节点继续依节点到期/逾期提醒。
- 已读通知、讨论、补充要求和要求回复不刷新有效进展时间，不改变完成状态；已生效的未完成任务仍在待办中。
- 本轮不新增完成审批。继续按原有任务规则，由负责人或授权管理者反馈，保留真实操作者；自行安排的两级审核保持原样。
- 周月报可手动查看、复制、下载和保存。重复生成同一期返回已有版本，明确“另存新版本”才新增；已保存报告不会被任务改名、转交或补录静默覆盖。
- 自动报告对进行中的项目生成团队报告及有效非只读成员个人报告，站内通知给报告本人；项目管理员可关闭周报/月报。历史报告读取仍检查当前项目、任务权限。
- 校园“存量学校”按已签约/运营中分类；学校转化需要人工说明依据，不把任务完成自动等价为开票、到账或营收。
- 默认合同页显示当前年有效合同（签订年），切年份和月份后卡片/下钻/导出共用过滤条件。全历史累计单独可选，不删除旧年合同。

## 数据来源和外部依赖

`来源对账` 使用已经保存的企微快照，标明源表版本、最近同步和最近检查。若外部授权失败，继续展示上次完整快照和错误，不将它标为实时新数据。合同金额、累计回款及学校运营收入分别核对。

发布前只读检查发现，合同工作簿的企微机器人“文档”权限已过期。实时读取恢复需要原机器人创建者完成授权；此前快照继续可用。没有通过技术手段扩大外部数据权限。

企微消息的队列、收件人权限、失败重试及任务完成后停止投递均在隔离测试中验证。真实员工收件回执、业务方对账确认与实际团队使用反馈须据事实记录，不能用测试通过替代。

本次对服务器的只读检查确认企微自建应用可读取且未停用；此检查未发送测试消息。文档机器人授权与自建应用消息是两个独立通道，前者过期不应被表述成所有企微接口不可用。

迁移在独立空库验证全链升级，并验证本次迁移回退到 `14e5d891aff2` 后重新升级。生产升级不执行 seed。

发布使用 `SERVER=jucheng-ecs bash deploy/release.sh`。脚本要求发布源码已提交，重建前端并核对源码指纹；数据库、业务附件和旧页面先备份，旧 API 镜像单独保留。新 API 健康且版本匹配后才替换前端入口，已有页面使用的旧哈希资源仍保留。前端 `/build-info.json` 与后端 `/health` 的 revision 应相同。

回退在服务器执行 `bash /opt/jucheng/deploy/rollback-release.sh /opt/jucheng/deploy/releases/<明确发布目录>`。本轮为新增表迁移，回退只恢复旧程序和页面，保留新增业务记录及数据库；不使用旧备份覆盖发布后新增的数据。备份恢复演练应使用隔离库。

隔离备份恢复演练将浏览器验收库完整导出并恢复到另一个独立库，任务、节点反馈、讨论及已保存报告数量一致。原工作区已有变更的样例文件在测试前另存，测试后恢复为本轮开始时的内容，不纳入本次提交。

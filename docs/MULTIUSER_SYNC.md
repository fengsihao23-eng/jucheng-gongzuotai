# 多人协作下的数据一致性问题与同步方案

> 现状：FastAPI（uvicorn `--workers 2`）+ PostgreSQL 17 + Vue 3 SPA，单机 Docker Compose。
> 结论先说：**不是接入企业微信导致的**，是这套架构在单用户演示期没暴露、多人并发后必然出现的三类问题——进程内状态分裂、缺并发控制、缺变更推送。

## 一、哪些功能和数据不同步

| 功能 / 数据 | 现在看到的现象 | 直接原因 | 影响 |
|---|---|---|---|
| 经营看板、大屏 | A 改了合同/回款，B 的看板最多 5 分钟不变；同一时刻两人刷新，可能看到两组不同数字 | 看板结果存在进程内 TTL 缓存（300s），失效只在当前进程生效 | 高 |
| 合同 / 商机 / 报销 / 项目 / 工单 / 应收 列表 | 别人新增或修改的记录，不切页面就永远看不到 | 页面只在 `onMounted` 拉一次，无轮询、无推送 | 高 |
| 详情编辑（合同、项目、商机、工单、日记账） | 两人同时编辑同一条，后保存的静默覆盖前者，没有任何提示 | 全量 PUT 覆盖，无版本号/条件更新 | 高 |
| 业务编号（HT-/JC-/SJ-/KF-） | 两人同时新建，偶发 500 或保存失败 | 编号用 `MAX(no)+1` 生成，唯一约束撞车 | 中 |
| 角色 / 菜单权限 | 管理员改了某人权限，对方已打开的页面菜单不变，要重登 | 前端 `profile` 是登录时的快照，只存内存 | 中 |
| 系统字典、业务口径 | 改了以后报表/看板仍按旧口径，最多 5 分钟 | 同看板缓存 | 中 |
| 企微通讯录（人员/部门/岗位） | 新入职、离职、调岗最长 1 天才生效 | 只有每日 06:00 增量同步，未订阅通讯录变更事件 | 中 |
| MCP 接入（WorkBuddy） | 同一令牌的请求随机失败，需重连 | MCP 会话保存在单进程内存，两个 worker 各存一份 | 中 |
| 小聚任务 | 任务列表可见，但执行依赖单进程内的 Node 子进程 | 任务文件在共享卷，执行上下文在进程内 | 低 |
| 审批归集 | 实时（回调正常），回调丢失时靠 5 分钟对账兜底 | — | 低 |

## 二、根因（四层）

### 1. 部署层：两个 worker，进程内状态不共享

生产启动命令是 `uvicorn --workers 2`，Nginx 轮询转发，同一个用户的相邻两个请求可能落在不同进程上：

- `app/services/board_service.py`：`_cache` + `invalidate()` 都是进程内的，A 写数据只清了 A 所在进程的缓存，另一个进程继续返回旧值。
- `app/integration/wecom/live.py`：`LiveWeCom._token` 每个进程各缓存一份，各自刷新，容易互相顶掉。
- `app/mcp_server/server.py`：限流 `_calls`、FastMCP `session_manager` 都在内存，MCP 客户端拿到 worker A 的会话、下次请求到 worker B 就会报会话不存在。
- APScheduler 在每个 worker 都起了一份，靠 Postgres advisory lock 防重复，这部分是安全的。

### 2. 数据层：没有并发控制

- 所有编辑接口是“读详情 → 前端改 → 全量 PUT 回去”，服务端不校验版本，天然丢更新。
- `app/services/codes.py` 用 `MAX()+1` 生成编号，两个事务同时读到同一个最大值就撞唯一约束，异常直接冒到 500。
- 没有变更事件表/outbox，写操作完成后没有任何“谁改了什么”的广播载体。

### 3. 接口层：只有拉，没有推

- 没有 SSE / WebSocket 端点，前端无法感知他人变更。
- 响应没有 `ETag` / `Last-Modified` / `X-Data-Version`，连低成本的条件轮询都做不了。
- 列表接口没有 `updated_since` 增量参数，只能整页重拉。

### 4. 前端层：一次加载，长期持有

- 各页面 `onMounted` 拉一次数据，之后只有本页操作会刷新；切换路由才重新拉。
- 没有跨标签页同步（`storage` 事件未使用），同一浏览器开两个标签也会不一致。
- 权限菜单是登录时快照，服务端改了角色不会主动下发。

## 三、解决方案

### P0｜当天可落地，先止痛（推荐立刻做）

1. **消除进程内状态分裂**，二选一：
   - **方案 A（推荐，最省事）**：`--workers 1`。80 人内网规模、读多写少，单进程 + async 完全够用，改一行 Dockerfile 即可让缓存、会话、限流立刻一致。
   - **方案 B（要保留多进程时）**：把看板缓存、限流、MCP 会话挪到外部（Redis 或 Postgres），失效用 `pg_notify` 广播。
2. **看板缓存 TTL 300s → 60s**，并在看板/大屏加“手动刷新”按钮（后端已支持 `refresh=1`，前端没接）。
3. **当前页轻量轮询**：列表页和看板每 30s 静默重拉一次；`document.hidden` 时暂停，避免无谓请求。改动集中在 `frontend/src/views/*` 和 `api/client.js`，不动后端。

验收：A 改数据后，B 在不刷新的情况下 ≤60s 看到新值；两人刷新看到同一组数字。

### P1｜3–5 天，解决“写坏”

4. **乐观锁**：给 `biz_contract / biz_project / biz_opportunity / cs_ticket / fin_journal` 等加 `version` 整型列（或用 `updated_at` 做条件），PUT 时带 `expected_version`，冲突返回 `40901` 并附最新数据；前端提示“该记录已被他人修改，请对比后重试”。
5. **编号原子化**：建 `biz_sequence(prefix, year, seq)` 表，用 `UPDATE ... SET seq = seq + 1 RETURNING seq` 或直接建 PG sequence；撞唯一约束时自动重试一次。
6. **权限即时生效**：路由切换时 `fetchMe()`；或 `/auth/me` 加 60s 轮询，菜单变化立即重渲染。

验收：并发编辑 20 次无静默覆盖；并发新建 20 次编号全唯一且无 500；改权限后对方 60s 内菜单更新。

### P2｜1–2 周，走向实时协同

7. **SSE 事件总线**：新增 `GET /api/v1/events`（Server-Sent Events）。写操作提交后 `pg_notify('portal_events', json)`，服务端 LISTEN 后按用户权限推 `{type, entity, id, scope}`；前端 `EventSource` 收到只做“失效 + 重拉当前页”，不传业务数据。
   - 选 SSE 不选 WebSocket：只有服务端→客户端单向通知，Nginx 已支持，断线重连内置，改造成本最低。
8. **缓存与限流外置**：Redis 存看板聚合、限流计数、MCP 会话；保留 advisory lock 防重复任务。
9. **企微通讯录准实时**：订阅 `change_contact` 回调，成员/部门变更事件触发增量同步（复用 `company_directory_service.sync_confirmed_company`），把最长 1 天延迟压到秒级；或先把定时同步提到每小时。
10. **MCP 会话粘性**：Nginx 对 `/mcp` 做 `ip_hash` 或 cookie 粘性；或改成无状态 + 外部 session store。

验收：跨用户数据可见延迟 P95 < 2s；MCP 会话失败率 < 1%；通讯录变更 < 1 分钟生效。

## 四、不建议的做法

- 用 WebSocket 给每个客户端推全量列表：流量和一致性维护成本都高，SSE + 失效重拉足够。
- 前端 1–2s 全表轮询：把一致性问题转成数据库压力问题。
- 直接加副本数（多容器/多机）而不先解决会话、缓存、限流的外置：分裂会更严重。
- 给所有表无差别加版本号：只给“多人会同时改”的业务主表加，配置类表用缓存失效即可。

## 五、建议的推进顺序

先做 P0 的三项（半天内可上线，用户感知立刻改善）→ 再做 P1 的乐观锁和编号（消除数据损坏风险）→ 最后做 P2 的 SSE 与通讯录回调（体验升级）。

判断标准很简单：**在 P0 完成后，如果“两个人同时刷新看到的数字不一样”这个现象消失，就说明进程内状态分裂已被消除**，后面都是在这之上的增强。
